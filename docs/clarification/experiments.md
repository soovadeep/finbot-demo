# Clarification experiments

This branch adds a local, bounded clarification workflow before Finbot's existing
financial-answer pipeline. It is a development experiment, not a completed human
study or a claim of improved live-model accuracy. The paper draft is unchanged.

For the consolidated notation, equations, design decisions and implementation status,
start with [clarification design and mathematics](design.md).

## Run the demo

Install the repository requirements in a Python 3.11+ environment, then run:

```sh
python -m finbot.demo --port 8766
```

Open <http://127.0.0.1:8766/study> for the current [message-driven demo](conversation.md).
Open <http://127.0.0.1:8766/clarification> for the original mathematical inspector
described below. The financial evidence inspector remains available at `/inspector`.
The server binds to loopback, enforces the existing host/origin
checks, accepts no credentials and makes no paid or live-model calls.

Try these paths in the original mathematical inspector:

1. Start **Two possible payments**. Inspect the ranked template questions, select
   **Bank transfer**, then **Greenway**, and confirm `txn_BANK0002`. The final
   answer is generated by the scripted adapter and checked by Finbot's real gate.
2. Confirm `txn_CARD0001`, then correct it to `txn_BANK0002`. The revision changes;
   only the newly selected record appears in current financial evidence. The
   earlier selection remains in the dialogue audit, marked as invalidated.
3. Reply **I'm not sure** to both questions. The question budget runs out without
   producing a financial answer. **None of these records** also leaves the task
   unresolved, including after an earlier answer.
4. Select **Mistaken failure assumption**. The pending record produces a pending
   status explanation, without accepting the premise that it was declined.
5. Inject an invented fee in both draft and repair, confirm a record, and inspect
   the actual verifier rejections and record-summary fallback.
6. Compare **No clarification questions**, **Fixed template order**, **Expected
   information gain**, and **Expected error reduction minus cost**. All runtime
   strategies still require explicit record confirmation; posterior confidence
   never authorizes access or substitutes for confirmation.

## Original inspector boundaries

The following details describe `ClarificationSession` and `/clarification`. The
v2 conversation has [different interpretation and stopping rules](conversation.md):
it consumes free-form details with limited rules, skips supplied/unavailable fields,
and suggests a single working match without waiting for a probability threshold.

- `finbot/clarification.py` provides three reusable template types: payment kind,
  merchant/recipient, and date. Templates with missing or nondiscriminating
  attributes are excluded. It supports 1–8 already authorized candidates.
- Beliefs update using Bayes' rule. The finite response channel includes a
  definite correct option, symmetric mistakes among other options, and an
  uninformative `I'm not sure` outcome. Unknown free text is treated as that
  outcome; impossible observations retain the prior and record a model mismatch.
- The inspector calculates expected information gain in bits and one-step
  reduction in zero-one record-selection error. The decision-value selector
  subtracts 0.02 error units per question; this is an experimental setting.
- A conversation asks at most two questions by default (three is the library
  maximum). No question template repeats. A 0.95 posterior stops further
  elicitation but does not confirm the record.
- After confirmation, the inspector labels the explicit selection rather than
  displaying a model probability of 100%. Confirmation can still be mistaken;
  it is an operational instruction, not a measurement of the user's latent intent.
  Rejecting the catalogue clears the answer and hides inapplicable probabilities.
- The server supplies a fixed synthetic tenant-scoped catalogue. HTTP clients
  cannot supply records, evidence, posteriors, tenants or model configuration.
  Selecting a record outside the catalogue is rejected.
- Each explicit confirmation runs fresh retrieval and verification through
  `run_demo`. It does not carry previous financial facts, drafts, or verifier
  output into a corrected answer. The fixed task is explaining the selected
  record's status and details; arbitrary goal changes are not interpreted yet.
- A pending payment no longer receives the generic failure guidance intended
  for unrecognized failures. This does not add a pending-payment retry policy.

The response model assumes independent replies given the intended record and
question. Its parameters are visible assumptions, not human-calibrated estimates.
The question bank and catalogue are deterministic. LLM question generation,
automatic candidate discovery, persistent production sessions, free-text intent
inference, and personalized factor models remain future work. Existing model
adapters serve the downstream answer pipeline; this experiment does not claim
an LLM generates or learns the clarification policy.

## Reproduce the simulation

```sh
python scripts/evaluate_clarification.py --question-budget 1 --out results/clarification/one-question.json
python scripts/evaluate_clarification.py --question-budget 2 --out results/clarification/synthetic.json
python -m unittest tests.test_clarification tests.test_demo
```

With Playwright installed and the server running, the optional browser check is
`node scripts/check_clarification_ui.cjs`. `FINBOT_CHROME` can name an installed
Chrome executable; `FINBOT_UI_OUTPUT` optionally selects a screenshot directory.

The script enumerates every target and reply path under specified probabilities.
It uses 24 authored scenario families with 2–4 candidate records, five response
regimes, and four selectors plus a supplied-correct-intent control: **600 comparison
rows per budget**, not 600 independent conversations or Banking77 cases. There
is no sampling seed because enumeration is exact. Source hashes accompany each
report. Families include shared identifying attributes and indistinguishable
metadata. All are development fixtures; none is held out.

Regimes: matched reliable replies; matched noisy replies; matched uninformative
replies; an overconfident assumed model paired with noisier actual replies; and
correlated mistakes caused by a persistent alternative target. The last two
explicitly challenge the selector's assumptions.

Metrics measure MAP record selection and the question budget. Optional 0.95
threshold coverage/error diagnostics show confidence failure; they do not
describe the actual release rule. Targets are always in the catalogue. Results
do not measure final-answer factuality, human effort, usefulness, latency, or API
cost. Exact expectations under a toy model do not warrant statistical confidence
intervals or claims about human populations.

## Next empirical step

The [structured participant pilot](study.md) now implements a local
collection screen, completed-session exports, development response fitting,
model freezing, and guarded evaluation. Open `/study/probes` to rehearse it. Its authored
pilot tasks and automated checks are not human study results.

The default `/study` page is now the [message-driven conversation demo](conversation.md):
initial details are consumed, tentative replies retain alternatives, and private
role-play notes/reference targets do not enter the assistant's inference.

Collect consented replies to assigned tasks with known intended records. Record
question type, wording, option order, reply, and corrections. Estimate response
channels on development participants, pooling across question types where data
are sparse. Keep participants and related scenario families separate between
development and held-out evaluation, and freeze the selector before evaluation.
Compare fixed, information-gain and decision-value selectors at equal budgets,
alongside no-question and supplied-information controls. Measure correct intended
record plus independently judged factual support, completion, abstention,
questions, correction recovery, latency and cost. Synthetic reply distributions
and unit-test pass rates do not replace these measurements.

## Local validation

The initial clarification commit `4ac89ee` passed the full 643-test unit suite (22 new clarification
tests), Ruff, and mypy over 99 source files. Scripted evaluation passed 41/41
development and 185/185 test expectations. The defended red-team configuration
stopped 34/34 authored attacks and handled 7/7 benign cases. These existing
expectations do not establish final-answer helpfulness or semantic accuracy.

Browser acceptance checks exercised posterior updates, explicit confirmation,
correction evidence isolation, unresolved replies, all six presets, injected
failure repair/fallback, JSON trace export, the original inspector, and 320/390px
layouts, with no JavaScript errors. The focused tests and browser checks were
rerun after the final display changes. Docker and hosted CI were not run.

The later conversation-demo commit `edeaaa8` passed 685 unit tests, Ruff and mypy
over 101 source files. Browser checks covered the v2 conversation and the retained
v1 collector: consuming complete messages without questions, tentative alternatives,
unavailable dates, corrections, missing records, reference separation, exports and
mobile layouts. These are software checks, not human-performance results.
